## 第一章：使用 STM32CubeMX 创建 STM32F407VET6 工程

### 1.1 本章目标

使用 STM32CubeMX 创建一个可在 Keil MDK 中编译、下载和调试的基础工程。

当前硬件和软件条件：

| 项目 | 配置 |
|---|---|
| 主控芯片 | STM32F407VET6 |
| 封装 | LQFP100 |
| 外部高速晶振 | 8 MHz HSE |
| 目标系统时钟 | 168 MHz |
| 调试接口 | SWD |
| 开发工具 | STM32CubeMX |
| 编译工具 | Keil MDK-ARM V5.32 |
| STM32Cube 固件包 | STM32Cube FW_F4 V1.28.3 |
| CubeMX 工程文件 | RTOS_F4.ioc |

> 说明：本章先建立可以正常运行的基础工程，FreeRTOS 的配置和任务创建放在后续章节记录。

### 1.2 创建新工程

1. 打开 STM32CubeMX。
2. 点击 `File -> New Project`。
3. 进入 `MCU/MPU Selector`。
4. 在 `Part Number` 搜索框中输入：

   ```text
   STM32F407VETx
   ```

5. 在搜索结果中选择 `STM32F407VETx`。
6. 确认芯片信息后，点击 `Start Project`。
7. 如提示保存工程，将工程命名为 `RTOS_F4`。

### 1.3 配置系统调试接口

进入 `Pinout & Configuration -> System Core -> SYS`：

1. 将 `Debug` 设置为：

   ```text
   Serial Wire
   ```

2. 确认以下引脚自动分配给 SWD：

   ```text
   PA13 -> SYS_JTMS-SWDIO
   PA14 -> SYS_JTCK-SWCLK
   ```

3. 保留 `SysTick` 作为 HAL 和后续 RTOS 的时基。

如果不配置 SWD，程序下载后可能无法再次使用 ST-Link 正常连接和调试。

### 1.4 配置 8 MHz 外部晶振

进入 `Pinout & Configuration -> System Core -> RCC`：

1. 将 `High Speed Clock (HSE)` 设置为：

   ```text
   Crystal/Ceramic Resonator
   ```

2. 确认以下引脚自动配置为外部晶振接口：

   ```text
   PH0-OSC_IN  -> RCC_OSC_IN
   PH1-OSC_OUT -> RCC_OSC_OUT
   ```

3. 确认板上的外部晶振实际频率是 `8 MHz`。

> 注意：CubeMX 中填写的 HSE 频率必须与板子实际焊接的晶振频率一致。频率填错会导致系统时钟计算错误。

### 1.5 配置系统时钟树

进入 `Clock Configuration` 页面，按以下参数配置。

#### 1.5.1 PLL 参数

| 参数 | 配置值 |
|---|---:|
| HSE 输入频率 | 8 MHz |
| PLL Source Mux | HSE |
| PLLM | 8 |
| PLLN | 336 |
| PLLP | 2 |
| PLLQ | 4（当前工程，未启用 USB） |

#### 1.5.2 系统时钟和总线分频

| 参数 | 配置值 | 输出频率 |
|---|---:|---:|
| System Clock Mux | PLLCLK | 168 MHz |
| AHB Prescaler | `/1` | HCLK = 168 MHz |
| APB1 Prescaler | `/4` | PCLK1 = 42 MHz |
| APB2 Prescaler | `/2` | PCLK2 = 84 MHz |
| Flash Latency | 5 WS | 适用于 168 MHz、3.3 V |
| Voltage Scale | Scale 1 | 高性能模式 |

#### 1.5.3 时钟计算关系

```text
HSE 8 MHz / PLLM 8 = 1 MHz PLL 输入（通常选择 1 MHz～2 MHz，这里选择 1 MHz）
1 MHz * PLLN 336 = 336 MHz VCO（PLL 压控振荡器 VCO 的范围通常为 100～432 MHz。为了让最终 SYSCLK 达到 168 MHz，这里选择 336 ）
336 MHz / PLLP 2 = 168 MHz SYSCLK
APB1 分频为 4，得到最大值 42 MHz，时钟倍频为 84 MHz
APB2 分频为 2，得到最大值 84 MHz，时钟倍频为 168 MHz
```

当前工程没有启用 USB、SDIO 等需要 48 MHz 时钟的外设，因此 PLLQ 使用了 4。

如果后续启用 USB Full Speed，需要将 `PLLQ` 改为 `7`：

```text
336 MHz / 7 = 48 MHz
```

并确认 CubeMX 的 USB 时钟为 `48 MHz`。不能在只修改 USB 外设的情况下继续保留 `PLLQ=4`。

### 1.6 配置基础 GPIO

根据硬件需要配置 GPIO。当前工程使用 `PA1` 作为普通输出，可作为后续板级测试点。

进入 `Pinout & Configuration`，在右侧芯片视图中点击 `PA1`：

1. 选择 `GPIO_Output`。
2. 打开 `System Core -> GPIO`。
3. 根据需要设置：

   ```text
   GPIO output level
   GPIO mode: Output Push Pull
   GPIO Pull-up/Pull-down: No pull-up and no pull-down
   Maximum output speed
   User Label
   ```

实际产品引脚应按照硬件原理图配置，不要仅照搬示例引脚。

### 1.7 配置工程生成选项

进入 `Project Manager`。

#### 1.7.1 Project 页面

配置以下内容：

| 参数 | 配置值 |
|---|---|
| Project Name | RTOS_F4 |
| Application Structure | Basic |
| Toolchain/IDE | MDK-ARM V5.32 |
| Firmware Package | STM32Cube FW_F4 V1.28.3 |

#### 1.7.2 Code Generator 页面

建议确认以下选项：

1. 勾选 `Generate peripheral initialization as a pair of .c/.h files per peripheral`。
2. 保留 `Keep User Code when re-generating`。
3. 不要删除生成的工程文件。

用户代码必须写在类似下面的注释区间内：

```c
/* USER CODE BEGIN ... */

/* USER CODE END ... */
```

CubeMX 重新生成代码时通常会保留这些区间，其他自动生成区域可能被覆盖。

### 1.8 生成代码

1. 点击 `Project -> Generate Code`。
2. 等待 CubeMX 完成代码生成。
3. 确认没有出现红色错误提示。
4. 打开生成的 `MDK-ARM` 目录。
5. 双击 `RTOS_F4.uvprojx`，使用 Keil MDK 打开工程。

### 1.9 编译、下载和运行

在 Keil MDK 中：

1. 点击 `Rebuild` 进行完整编译。
2. 确认编译结果为 `0 Error(s)`。
3. 在 `Options for Target -> Debug` 中选择 ST-Link 或其他实际使用的调试器。
4. 点击 `Download` 下载程序。
5. 复位开发板并确认程序能够正常运行。

可以先用一个 GPIO 翻转程序验证：

```c
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_1);
HAL_Delay(500);
```

### 1.10 生成结果检查

重新生成代码后，检查以下内容：

1. `RTOS_F4.ioc` 中 HSE 为 `8000000` Hz。
2. `stm32f4xx_hal_conf.h` 中应包含：

   ```c
   #define HSE_VALUE    8000000U
   ```

3. `main.c` 的 `SystemClock_Config()` 应使用：

   ```c
   RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_HSE;
   RCC_OscInitStruct.HSEState = RCC_HSE_ON;
   RCC_OscInitStruct.PLL.PLLSource = RCC_PLLSOURCE_HSE;
   RCC_OscInitStruct.PLL.PLLM = 8;
   RCC_OscInitStruct.PLL.PLLN = 336;
   RCC_OscInitStruct.PLL.PLLP = RCC_PLLP_DIV2;
   ```

4. 系统时钟源应为 `PLLCLK`。
5. AHB 分频为 `/1`。
6. APB1 分频为 `/4`。
7. APB2 分频为 `/2`。
8. Flash 等待周期为 `FLASH_LATENCY_5`。

### 1.11 本章常见问题

#### 问题 1：晶振频率填写错误

如果实际晶振是 8 MHz，但 CubeMX 中填写为 25 MHz，会导致：

- PLL 输入频率计算错误
- 系统时钟频率错误
- FreeRTOS SysTick 节拍不准确
- 串口波特率和定时器周期不正确

正确关系必须保持为：

```text
PLL 输入 = HSE / PLLM = 8 MHz / 8 = 1 MHz
```

#### 问题 2：只启用 HSE，没有切换到 PLLCLK

只配置 HSE 但 `System Clock Mux` 仍选择 HSI，程序仍然不会运行在 168 MHz。必须确认：

```text
System Clock Mux = PLLCLK
```

#### 问题 3：APB1 或 APB2 超过最大频率

STM32F407 的 APB 总线上限：

```text
APB1 <= 42 MHz
APB2 <= 84 MHz
```

因此 168 MHz 主频下必须使用：

```text
APB1 Prescaler = /4
APB2 Prescaler = /2
```

#### 问题 4：系统运行异常或程序停在 Error_Handler

优先检查：

1. 板上是否真实存在 8 MHz 晶振。
2. 晶振和负载电容是否焊接正常。
3. CubeMX 中 HSE 是否选择 `Crystal/Ceramic Resonator`。
4. `HSE_VALUE` 是否为 `8000000U`。
5. `PLLM` 是否为 `8`。
6. 供电电压和 Flash 等待周期是否正确。

#### 问题 5：重新生成代码后找不到用户代码

检查用户代码是否写在 `USER CODE BEGIN/END` 区间之外。写在自动生成区域的代码可能被 CubeMX 覆盖。

### 1.12 本章结果

完成本章后，工程应满足：

- 主控为 STM32F407VET6
- 使用 8 MHz 外部晶振
- SYSCLK 和 HCLK 为 168 MHz
- APB1 为 42 MHz
- APB2 为 84 MHz
- 可在 Keil MDK 中编译
- 可通过 SWD 下载和调试
- 已具备后续添加 FreeRTOS 的基础

## 第二章：启用 FreeRTOS 与配置 HAL 时基

### 2.1 本章目标

在现有 STM32F407VET6 工程中启用 FreeRTOS，并正确区分：

- FreeRTOS 系统节拍
- HAL 库时基
- 中断优先级
- 任务优先级和任务栈

### 2.2 启用 FreeRTOS

进入：

```text
Pinout & Configuration -> Middleware and Software Packs -> FREERTOS
```

配置以下内容：

| 参数 | 当前配置 |
|---|---|
| Interface | CMSIS_V2 |
| TICK_RATE_HZ | 1000 |
| 内核时基 | SysTick |
| 内存管理 | heap_4 |
| 新建任务 1 | led1_task，Normal 优先级 |
| 新建任务 2 | led2_task，Low 优先级 |

当前 FreeRTOS 节拍为：

```text
1000 Hz = 1 ms
```

### 2.3 将 HAL 时基改为 TIM7

进入：

```text
Pinout & Configuration -> System Core -> SYS
```

将：

```text
Timebase Source
```

从 `SysTick` 改为：

```text
TIM7
```

最终分工为：

```text
TIM7    -> HAL_Delay、HAL_GetTick、HAL 外设超时
SysTick -> FreeRTOS 任务调度、osDelay、任务超时
```

选择 TIM7 而不是 TIM6 的原因：

- TIM6 和 TIM7 都是基本定时器，都可以作为 HAL 时基
- STM32F407 的 TIM6 与 DAC 共用中断向量 `TIM6_DAC_IRQn`
- 如果后续使用 DAC 中断，TIM7 的中断向量独立，冲突更少
- 当前工程中 TIM7 没有被其他功能占用

TIM7 当前计算关系：

```text
APB1 timer clock = 84 MHz
预分频后计数时钟 = 1 MHz
每计 1000 个数产生一次中断
TIM7 中断周期 = 1 ms
```

### 2.4 确认 FreeRTOS 仍使用 SysTick

CubeMX 的 Cortex-M4 FreeRTOS 移植层默认使用 SysTick，没有单独的“FreeRTOS Tick Source”下拉框。

确认方式如下。

#### 2.4.1 检查 CubeMX

在 `System Core -> SYS` 中，HAL 时基应显示：

```text
TIM7
```

在 `Middleware and Software Packs -> FREERTOS` 中，FreeRTOS 应保持启用。

#### 2.4.2 检查生成代码

`Core/Src/stm32f4xx_it.c` 中应包含 TIM7 的 HAL 时基中断：

```c
void TIM7_IRQHandler(void)
{
  HAL_TIM_IRQHandler(&htim7);
}
```

`main.c` 中应通过 TIM7 周期回调更新 HAL tick：

```c
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
  if (htim->Instance == TIM7)
  {
    HAL_IncTick();
  }
}
```

FreeRTOS 的 SysTick 处理来自：

```text
Middlewares/Third_Party/FreeRTOS/Source/CMSIS_RTOS_V2/cmsis_os2.c
```

核心调用为：

```c
xPortSysTickHandler();
```

因此，SysTick 不再负责 HAL tick，而是专门服务 FreeRTOS。

### 2.5 GPIO 名称和配置文件位置

GPIO 的 User Label 最终生成到：

```text
Core/Inc/main.h
```

当前工程的 GPIO 定义：

```c
#define LED2_Pin GPIO_PIN_1
#define LED2_GPIO_Port GPIOA

#define LED_GREEN_Pin GPIO_PIN_2
#define LED_GREEN_GPIO_Port GPIOA
```

各文件职责：

| 文件 | 作用 |
|---|---|
| `RTOS_F4.ioc` | 保存 CubeMX 中的 GPIO User Label |
| `Core/Inc/main.h` | 保存生成的 GPIO 引脚宏定义 |
| `Core/Src/gpio.c` | 配置 GPIO 输入输出模式、速度和上下拉 |
| `Core/Src/freertos.c` | 保存 `led1_task`、`led2_task` 等任务名称 |

修改 GPIO 名称时，应在 CubeMX 中点击对应引脚并修改 `User Label`，然后重新生成代码。

不要只修改 `main.h`，否则下次 CubeMX 重新生成时可能被覆盖。

### 2.6 当前任务配置

当前创建了两个任务：

| 任务 | 优先级 | 栈大小 | 当前行为 |
|---|---|---:|---|
| `led1_task` | Normal | 512 Byte | `osDelay(1)` |
| `led2_task` | Low | 512 Byte | `osDelay(1)` |

FreeRTOS 任务中应使用：

```c
osDelay(100);
```

不要使用：

```c
HAL_Delay(100);
```

`HAL_Delay()` 是忙等待，不会让出 CPU。高优先级任务如果长时间忙等待，会阻塞低优先级任务。

后续增加功能时，高优先级任务仍必须保留 `osDelay()`、信号量等待或队列等待。否则低优先级任务可能永远得不到执行。

### 2.7 中断优先级检查

当前关键中断优先级：

| 中断 | 优先级 |
|---|---:|
| `SVCall_IRQn` | 0 |
| `TIM7_IRQn` | 15 |
| `SysTick_IRQn` | 15 |
| `PendSV_IRQn` | 15 |

FreeRTOSConfig.h 中设置：

```c
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
```

以后如果 UART、CAN、SPI、定时器等中断里调用：

```c
osMessageQueuePutFromISR()
osSemaphoreRelease()
osEventFlagsSet()
```

这些中断的抢占优先级必须设置为 `5～15`。

如果使用 `0～4` 的中断调用 FreeRTOS API，可能触发断言或破坏调度器状态。

### 2.8 当前冲突检查结果

#### 已确认正常

- HSE 为 8 MHz
- `HSE_VALUE` 为 `8000000U`
- SYSCLK 和 HCLK 为 168 MHz
- APB1 为 42 MHz
- APB2 为 84 MHz
- HAL 时基为 TIM7
- FreeRTOS 节拍为 SysTick
- TIM7 和 SysTick 均配置为最低抢占优先级 15
- 当前任务都调用了 `osDelay()`，暂时不存在任务饿死
- Core 目录中没有重复生成 SysTick、SVC 和 PendSV 的冲突处理函数

#### 历史编译问题：Newlib 重入选项（已解决）

`Core/Inc/FreeRTOSConfig.h` 曾启用：

```c
#define configUSE_NEWLIB_REENTRANT 1
```

但当前 Keil 工具链是 ARMCC 5，不是 Newlib。实际编译报错：

```text
cannot open source input file "reent.h": No such file or directory
```

解决方法：

1. 打开 CubeMX 的 `FREERTOS -> Config parameters`
2. 将 `USE_NEWLIB_REENTRANT` 设置为 `Disabled`
3. 重新执行 `Project -> Generate Code`
4. 在 Keil 中重新编译

不要在仅使用 ARMCC 5 且未提供 Newlib 的工程中启用该选项。

当前 `FreeRTOSConfig.h` 已不再定义 `configUSE_NEWLIB_REENTRANT`，Keil 编译结果已恢复为：

```text
0 Error(s), 0 Warning(s)
```

#### 后续需要注意的问题

1. 当前未启用栈溢出检查。增加复杂任务后，应启用 `configCHECK_FOR_STACK_OVERFLOW`。
2. 当前未启用内存分配失败钩子。后续动态创建队列、信号量和任务时，建议启用 `configUSE_MALLOC_FAILED_HOOK`。
3. 当前 PLLQ 为 4，不提供 48 MHz。现在未使用 USB，因此没有问题；启用 USB Full Speed 时应将 PLLQ 改为 7。
4. Keil 工程中的目标时钟仍显示 25 MHz。它不影响固件实际时钟，但建议在 `Options for Target -> Target -> Xtal` 中改为 8 MHz。
5. `HAL_TIM_PeriodElapsedCallback()` 是所有定时器共用的回调。以后增加其他定时器时，应继续判断 `htim->Instance`，不要重复定义该函数。

### 2.9 验证流程

Newlib 重入问题解决后，按以下顺序验证：

1. 在 Keil 中执行 `Rebuild`，确认 `0 Error(s)`。
2. 确认 `TIM7_IRQHandler()` 调用 `HAL_TIM_IRQHandler(&htim7)`。
3. 确认 FreeRTOS 的 SysTick 调用 `xPortSysTickHandler()`。
4. 在 `led1_task` 和 `led2_task` 中设置断点，确认两个任务都能运行。
5. 使用 `osKernelGetState()` 确认调度器处于运行状态。
6. 使用 `osThreadGetStackSpace()` 或 `uxTaskGetStackHighWaterMark()` 观察任务剩余栈空间。
7. 长时间运行并检查是否进入 `HardFault_Handler`、`Error_Handler` 或 FreeRTOS 断言。

### 2.10 本章结论

当前 `TIM7 + SysTick` 的时基分工没有直接冲突。

`configUSE_NEWLIB_REENTRANT` 引起的 `reent.h` 编译问题已经解决，当前工程可以通过编译。

## 第三章：疑难问题——Keil 无法连接目标芯片

### 3.1 问题现象

在 Keil MDK 中编译正常，但点击 `Download` 或 `Debug` 时出现：

```text
Target DLL has been cancelled
```

后续在 ST-Link 设置中显示：

```text
No target connected
```

### 3.2 已确认不是代码或芯片包问题

#### 3.2.1 源码编译正常

使用 Keil 批处理重新构建当前工程，结果为：

```text
0 Error(s), 0 Warning(s)
```

因此 `Target DLL has been cancelled` 不是 C 源码编译错误。

#### 3.2.2 STM32F4 器件包安装正常

器件包安装在：

```text
D:\Packs\Keil\STM32F4xx_DFP\3.1.1
```

下载算法文件存在：

```text
D:\Packs\Keil\STM32F4xx_DFP\3.1.1\CMSIS\Flash\STM32F4xx_512.FLM
```

Keil 的 `TOOLS.INI` 已正确设置：

```ini
RTEPATH="D:\Packs"
```

因此不是 F4 芯片包未安装或 Keil 找不到下载算法的问题。

#### 3.2.3 ST-Link USB 驱动正常

Windows 已识别：

```text
ST-Link Debug
ST-Link Virtual COM Port (COM5)
```

ST-Link 调试驱动和虚拟串口驱动均正常。

### 3.3 使用 STM32CubeProgrammer 直接诊断

为排除 Keil 配置的影响，使用 STM32CubeProgrammer CLI 直接连接。

普通模式：

```powershell
STM32_Programmer_CLI.exe -c port=SWD mode=normal freq=1000
```

复位下连接：

```powershell
STM32_Programmer_CLI.exe -c port=SWD mode=UR reset=HWrst freq=1000
```

两次结果均显示：

```text
ST-LINK FW : V2J43M28
Voltage    : 3.29V
Error: Unable to get core ID
Error: No STM32 target found!
```

诊断结果：

- ST-Link 自身正常
- ST-Link USB 通信正常
- 目标板供电检测正常
- 目标电压约为 `3.29 V`
- ST-Link 无法通过 SWD 读取 Cortex-M4 Core ID

因此问题位于 ST-Link 与 STM32F407 之间的 SWD 调试连接，或者芯片启动后的调试状态。

### 3.4 临时现象：BOOT0 接 3.3 V 才能连接

实际测试发现：

```text
BOOT0 = 3.3 V -> 可以识别并连接
BOOT0 = GND    -> No target connected
```

原因是 BOOT0 接高电平时，STM32F407 从系统存储区 Bootloader 启动，不运行用户 Flash 中的程序，因此不会出现用户程序占用或关闭 SWD 的情况。

该方式可以用于临时救砖或下载程序，但存在以下限制：

- BOOT0 为高时不会自动运行用户程序
- 下载完成后必须将 BOOT0 恢复为 GND，并复位芯片
- 不适合作为长期运行配置
- 调试用户程序时仍然不方便

### 3.5 可能原因

#### 可能原因 1：旧程序启动后关闭或占用了 SWD

之前烧录的程序可能重新配置了 PA13/PA14，或者进入低功耗状态，导致正常启动后无法在线上调试。

当前工程的 CubeMX 配置为：

```text
PA13 -> SYS_JTMS-SWDIO
PA14 -> SYS_JTCK-SWCLK
Debug -> Serial Wire
```

因此当前新程序本身没有主动关闭 SWD。

#### 可能原因 2：NRST 没有连接到 ST-Link

如果只连接了 SWDIO、SWCLK、3.3V 和 GND，而没有连接 NRST，Keil 的 `Connect under Reset` 无法控制 MCU 复位，不能抢在用户程序执行前建立连接。

#### 可能原因 3：SWDIO 与 SWCLK 接反

正确连接必须为：

```text
ST-Link SWDIO -> MCU PA13
ST-Link SWCLK -> MCU PA14
ST-Link GND   -> MCU GND
ST-Link 3.3V  -> MCU 3.3V
ST-Link NRST  -> MCU NRST
```

#### 可能原因 4：BOOT0 电路设计问题

如果 BOOT0 没有下拉电阻，可能受外部电路影响，导致芯片启动模式不稳定。

推荐电路：

```text
BOOT0 -> 10 kΩ -> GND
BOOT0 -> 跳线或排针 -> 3.3V
```

正常运行时 BOOT0 保持低电平；需要进入系统 Bootloader 时再短接到 3.3V。

### 3.6 推荐解决流程

#### 第一步：临时下载当前程序

1. 将 BOOT0 接到 3.3V
2. 复位开发板
3. 使用 Keil 或 STM32CubeProgrammer 下载当前工程
4. 将 BOOT0 恢复为 GND
5. 再次复位开发板

如果当前程序能够正常运行，说明 ST-Link、SWD 引脚和新固件均正常。

#### 第二步：执行一次完整擦除

如果 BOOT0 接地后仍然无法连接，可以在 BOOT0 为 3.3V 时使用 STM32CubeProgrammer 执行：

```text
Full Chip Erase
```

该操作会擦除芯片内全部用户 Flash 数据，只能在确认不需要旧数据时执行。

擦除后重新下载当前工程。

#### 第三步：连接 NRST 并启用 Connect under Reset

在 Keil 中设置：

```text
Options for Target -> Debug -> ST-Link Debugger -> Settings
Port = SWD
Max Clock = 1 MHz
```

选择：

```text
Connect under Reset
```

保持 BOOT0 为 GND，再次尝试下载或调试。

#### 第四步：检查目标电压和接线

在 ST-Link 设置中观察目标电压，应接近：

```text
3.3 V
```

检查：

- ST-Link 与目标板是否共地
- SWDIO、SWCLK 是否接反
- NRST 是否连接
- BOOT0 是否稳定为低电平
- 板载调试隔离跳线是否正确连接
- MCU 是否明显发热或短路

### 3.7 验证标准

问题解决后应满足：

1. BOOT0 保持 GND
2. ST-Link Settings 能识别到 STM32F407
3. `STM32_Programmer_CLI` 能读取 Core ID
4. Keil 可以正常下载程序
5. 复位后用户程序能够运行
6. 使用 `Connect under Reset` 可以正常进入调试

### 3.8 本章结论

当前已经排除：

- 源码编译问题
- STM32F4 器件包缺失
- ST-Link USB 驱动问题
- 目标板完全断电问题

当前问题集中在 SWD 调试连接。`BOOT0 = 3.3 V` 可以连接，说明调试器数据线基本正常，更像是有旧程序关闭 SWD、NRST 未连接或 BOOT0 启动模式异常。

临时下载可以将 BOOT0 接 3.3V；长期方案应为 BOOT0 接地、连接 NRST，并使用 `Connect under Reset`。
